# Звіт з лабораторної роботи №3
## Реалізація вимог продукту на bare metal (super loop): вимірювання швидкодії та пам’яті, пошук меж підходу

* **Дисципліна:** Системне програмування вбудованих систем
* **Тема проєкту:** Мультирежимний реєстратор інцидентів (Incident Recorder: Black Box)
* **Платформа:** STM32 NUCLEO-F411RE (Форма A — реальне обладнання)
* **Прошивка вимірювань:** `git=1f0dbc4`

### 1. Мета лабораторної роботи

1. Реалізувати функціональні вимоги PRD в **одній** bare-metal прошивці на моделі **super loop** (без RTOS).
2. Виміряти швидкодію (час задач, джитер, затримку реакції, CPU load) і використання пам’яті в сценаріях S1–S4 (навантаження + пошук меж).
3. Зафіксувати **реєстр обмежень** super loop з числовими доказами та базову лінію для порівняння з FreeRTOS у ЛР4.

### 3. Опис прошивки (super loop)

#### 3.1. Головний цикл
Порядок виклику в `app_run_step()`:

`cli → button → imu → baro → camera → journal → led`

Час ітерації вимірюється DWT (`STAT name=loop`). Періодичні задачі — time-triggered за `HAL_GetTick()`; подійні — за прапорцями стану.

Перелік задач і дедлайнів: `docs/tasks.md`.

#### 3.2. Діаграма потоку інциденту

```
[IDLE/ARMED]
    │  удар / tilt>60° / B1 / sim incident
    ▼
[INCIDENT] ──► capture QQVGA gray (~19 KiB)
    │
    ▼
 journal FSM: erase → wait busy → hdr+CRC → pages → DONE
    │
    ▼
 dump frame N  (UART hex → tools/dump_frame.py → PNG)
```

#### 3.3. Переривання
| IRQ | Навіщо |
|---|---|
| **SysTick** | `HAL_IncTick` — база періодів задач |
| Fault/NMI/… | стандартний CMSIS каркас |
| **USART/SPI/I2C IRQ** | не використовуються продуктом (polling HAL) |
| **EXTI кнопки** | не використовується (debounce у циклі) |

Під час рядка capture локальні IRQ вимикаються, щоб не втратити PCLK — це прямий внесок у джитер IMU (див. обмеження 1).

#### 3.4. Архітектура шарів
Збережено 4 рівні ЛР2 (`App` / `Devices` / `Platform` / `Core`). `scripts/check_deps.py` → **PASS** (немає HAL у App/Devices).

### 5. Методика вимірювань

| Канал | Що міряє | Де |
|---|---|---|
| **DWT CYCCNT** (`perf.c`) | min/avg/max задач, jitter IMU, btn_latency, LOAD % | `STATS`, `LOAD pct=` |
| **EVT мітки МК** | wall-time між подіями (btn, capture, flash) | `EVT t_us=… name=…` |
| **Stack painting** | used/reserve/free | `MEM` |
| **Linker** | FLASH/RAM, `.su` | `--print-memory-usage`, `-fstack-usage` |
| **Хост** | парсинг логів | `tools/analyze_log.py` |

Логічний аналізатор у цій команді **не застосовувався**. Для вимоги «два способи однієї метрики» використано **DWT STAT** і **EVT з міткою часу МК** (див. §6.3).

Сценарії: `docs/scenarios.md`. Сирі логи: `docs/metrics/`. Зведення: `docs/metrics/results.md`.

**Прогони:** S1 — idle; S2 — B1 + 27× повторні натискання (L2); S3 — `sim incident` + spam CLI; S4 — **8** повних інцидентів (стрес 6.2 / L5), частина з `Header verify FAIL`.

### 6. Результати за сценаріями

Повні таблиці: [`docs/metrics/results.md`](metrics/results.md).

#### 6.1. Зведена таблиця

| Метрика | S1 | S2 | S3 | S4 (стрес) |
|---|---|---|---|---|
| LOAD тип / пік | 17 / 17 | 17 / **45** | 17 / **54** | 17 / **63** |
| camera max | — | **377 мс** | **505 мс** | **531 мс** (n=8) |
| loop max | 18.6 мс | **425 мс** | **552 мс** | — (немає STATS) |
| IMU_JITTER max | 10.6 мс | **418 мс** | **551 мс** | ≈ capture |
| IMU missed | 25 | 21 | 27 | — |
| btn→capture_start | — | 24.0 мс | — | max **26.8 мс** |
| flash wall / OK | — | 414 мс / 1 | 399 мс / 1 | ~400 мс / **5 з 8** |
| stack used / free | 656 / 368 | 864 / 160 | 864 / 160 | — |

#### 6.2. Інтерпретація
* **S1:** `loop max≈baro` (~18.6 мс); LOAD≈17 % — запас CPU є.
* **S2/S3:** один capture → jitter/loop **сотні мс** (межа без витіснення).
* **S2 / L2:** 27× `btn_press` → лише 1 `incident`; **0** натискань у вікні `[CAM]` — під блоком кнопка не опитується; після інциденту FSM ігнорує B1 до `reset`.
* **FR-04** (старт capture): S4 max **26.8 мс** ≪ 300 мс (**PASS**). Тривалість кадру 340–531 мс — вартість GPIO QQVGA.
* **S3:** CLI spam не ронить відповіді, але подовжує capture (505 vs ~377 мс у S2).
* **S4 / L5:** при серії arm→incident→reset з’являється **точка зламу журналу**: 3/8 `Header verify FAIL` (~38 %). Це кількісний доказ межі FSM flash під агресивним циклом, не лише «повільності».

#### 6.3. Dual-measure (camera і btn)

| Метрика | DWT `STAT` | EVT (МК) | Δ |
|---|---|---|---|
| camera S2 | 377412 мкс | 390330 мкс | ≈13 мс |
| camera S3 | 505073 мкс | 518166 мкс | ≈13 мс |
| btn→incident S2 | 7344 мкс | 7345 мкс | ≈0 |

Розбіжність camera ≈ вартість логування/`perf`-обгортки — узгоджено.

#### 6.4. Порівняння з розрахунком
* IMU I²C @100 кГц ≈ **1.5 мс** ↔ `imu avg=1566 мкс`.
* QQVGA GPIO: очікувані сотні мс ↔ **340–531 мс**.
* W25Q64 erase+19200 B: datasheet/очікування ↔ wall **~400 мс**; FAIL у S4 — окремий клас (переривання FSM / verify), не лише «повільно».

### 7. Використання пам’яті

| Ресурс | Значення |
|---|---|
| `.text` + `.data` (FLASH) | 50932 B ≈ **9.7 %** від 512 KiB |
| `.data` + `.bss` (RAM) | 22504 B ≈ **17.2 %** від 128 KiB |
| Кадровий буфер `s_frame` | **19200 B** (найбільший `.bss`) |
| Heap | не використовується додатково продуктом (`sbrk` за замовчуванням) |
| Stack reserve (`_Min_Stack_Size`) | 1024 B |
| Stack used (painting) | S1: 656 B; S2/S3: **864 B** (free 160 B) |
| Найбільші `.su` (static) | `cli_dump_frame` 424 B, `task_journal` 328 B, `cli_dump_log` 176 B |

Запас стека під dump/journal достатній, але вільні 160 B у S3 — тримати під контролем у ЛР4 (окремі стеки задач зменшать «спільний» пік, але додадуть статичний RAM).

### 8. Реєстр обмежень (зведення)

Повний текст: [`docs/limitations.md`](limitations.md).

1. **Блокувальний capture** → IMU jitter до **551 мс** (S3), capture до **531 мс** (S4).
2. **Кнопка під CAM «німа»; у INCIDENT — ігнор повторів** (S2: 27 press / 1 incident).
3. **Flash ~400 мс** + під стресом S4 **38 % Header verify FAIL**.
4. **Жорстка зв’язність періодів** у `app_run_step`.
5. **Блокувальний I²C timeout** при відмові шини (L4).

Super loop виграє: детермінізм порядку, малий RAM footprint, просте налагодження.

### 10. Журнал інженерних проблем (≥5)

| # | Симптом | Root cause | Виправлення |
|---|---|---|---|
| 1 | `printf` float друкує порожньо | newlib nano без `_printf_float` | `-u _printf_float` у лінкері |
| 2 | Camera timeout / зависання | `HAL_GetTick` у hot-path PCLK + IRQ | timeout 1.5 с; IRQ off на рядок; без GetTick у циклі пікселів |
| 3 | `dump frame` → HardFault / обрив | важкий `sscanf` + довгі рядки | ручний hex-парсер, `[ACK]`, хост `--from-log` |
| 4 | Flash self-test FAIL / порожній dump | CS не high на старті; protect/SR | CS idle high; unlock; verify після hdr |
| 5 | Magic OK, `crc_ok=0` | padding/вирівнювання struct у CRC | `memcpy` полів у стабільний буфер перед CRC; dump дозволено з WARN |
| 6 | Кадр «шумний» на PNG | sync/регістри OV7670, не канал dump | прийнято для ЛР3; якість — backlog |
| 7 | S4: `Header verify FAIL` (3/8) | агресивний reset/повторний erase під час/після FSM | зафіксовано як межа; у ЛР4 — м’ютекс flash + заборона reset mid-write |

### 11. Висновок: чи потрібна ОС?

**Для поточного PRD — так, обґрунтовано потрібна (або DCMI+DMA без ОС).**

Числа:
* У спокої (S1) super loop **достатній**: LOAD≈17 %, FR-04 старт capture з запасом (S4 max 26.8 мс).
* **FR-01 ↔ фото:** capture дає **IMU_JITTER до ~0.55 с** — безперервні 100 Гц під час інциденту **недосяжні**.
* **FR-05/06 під стресом:** S4 показує не лише затримку, а й **втрату записів** (3 FAIL з 8) — межа спільного FSM без жорсткої серіалізації ресурсу.
* Кнопка під час CAM не фіксується (S2) — worst-case реакція ≈ довжина capture.

ОС (ЛР4): пріоритетне IMU, фоновий camera/journal, захист flash — перевірити тими ж S1–S4 (`baseline-lab4.md`).
