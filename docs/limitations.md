# Реєстр обмежень super loop (Lab 3)

Джерела: `docs/metrics/S1.log`…`S4.log`; `tools/analyze_log.py`.
Прошивка: `git=1f0dbc4`.

### Обмеження 1: Блокувальний захват кадру
**Симптом:** під час GPIO-capture періодичні задачі (IMU 100 Гц) не виконуються; зростає джитер і `missed`.  
**Доказ:** S1: `IMU_JITTER max=10.6 мс`. S2: camera **377 мс**, jitter **418 мс**. S3: camera **505 мс**, jitter **551 мс**. S4: capture max **531 мс** (n=8).  
**Причина:** немає витіснення; захват тримає CPU (IRQ off на рядок).  
**Обійти без ОС:** DCMI+DMA / FSM по рядках.  
**ОС:** IMU high prio + camera worker.  
**Гіпотеза ЛР4:** jitter S3/S4 ↓ ≥ на порядок.

### Обмеження 2: Подія під час довгої операції / у стані INCIDENT
**Симптом:** (а) під час `[CAM]` нові `btn_press` **не з’являються в лозі** — опитування кнопки стоїть; (б) після інциденту FSM ігнорує повторні B1 до `reset`.  
**Доказ:** S2: 27× `btn_press`, лише **1** `incident`; 0 натискань у вікні capture. S4: `btn→capture_start` max **26.8 мс** (коли кнопка *до* блоку) — FR-04 OK, але worst-case під час CAM ≈ довжина capture (**~0.3–0.5 с**).  
**Причина:** super loop + одноразовий стан INCIDENT.  
**Обійти без ОС:** EXTI+черга подій; дозволити повторний trigger за політикою.  
**ОС:** семафор від EXTI; окрема задача реакції.  
**Гіпотеза ЛР4:** p99 latency кнопки під час capture < 300 мс.

### Обмеження 3: Flash erase/program і збої verify під навантаженням
**Симптом:** wall-time flash ~400 мс; при швидких циклах arm→incident→reset частина записів падає з `Header verify FAIL`.  
**Доказ:** S2/S3: flash ≈399–414 мс, LOAD пік 45–54 %. S4: **5 OK / 3 FAIL** (~38 % відмов) при 8 інцидентах; LOAD пік **63 %**.  
**Причина:** довгий erase/program у спільному циклі; можливий `reset`/повторний erase до завершення попереднього FSM або читання «сирого» сектора.  
**Обійти без ОС:** жорсткіший FSM (не приймати reset mid-write), retry, DMA SPI.  
**ОС:** журнальна задача з блокуванням ресурсу flash.  
**Гіпотеза ЛР4:** IMU missed під час journal → 0; частка FAIL ↓ при серіалізації доступу.

### Обмеження 4: Модульність періодів
**Симптом:** новий період = правка `app_run_step` + defines.  
**Доказ:** `firmware/App/Src/app.c`.  
**Обійти без ОС:** таблиця time-triggered задач.  
**ОС:** `vTaskDelayUntil`.  
**Гіпотеза ЛР4:** нова задача без правки «чужого» циклу.

### Обмеження 5: Спільний I²C і блокувальний HAL timeout
**Симптом:** відмова сенсора → timeout роздуває ітерацію.  
**Доказ:** якісний L4; у S1–S4 шина здорова (`imu avg≈1.57 мс`).  
**Обійти без ОС:** короткий timeout, IT/DMA, bus recovery.  
**ОС:** драйвер у low-prio задачі + черга.  
**Гіпотеза ЛР4:** loop max під NACK зменшиться.

### Що super loop робить краще
- Детермінізм порядку задач.
- Малий RAM: stack used 656–864 B з reserve 1024 B.
- FLASH≈9.7 %, RAM≈17 % без N стеків RTOS.
- Поза довгими операціями FR-04 виконується з великим запасом (~7–27 мс).
